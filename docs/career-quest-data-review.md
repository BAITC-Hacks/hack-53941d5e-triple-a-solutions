## Что влияет на продукт

- 66 сотрудников не имеют `career_goal`. Предлагать цель с явной пометкой и возможностью выбора, не выдавать предположение за намерение сотрудника.
- 28 сотрудников хотят сменить роль. Нельзя всем рекомендовать только повышение в текущей роли. При этом цель не должна автоматически отменять условия допуска мероприятия.
- 16 сотрудников имеют грейд Lead. В наборе нет следующего грейда выше Lead; не придумывать его.
- 12 мероприятий имеют `prerequisites`; 4 обязательны и не являются кандидатами для добровольных рекомендаций.
- 9 мероприятий самостоятельные (`self_paced`), 10 очные и 21 онлайн по расписанию. Пустое расписание самостоятельного курса не означает недоступность.
- История содержит завершения, отказы, пропуски, прекращённые и текущие активности. Их следует учитывать раздельно; по пропускам нельзя утверждать, что сотрудник не мотивирован.
- Предпочтительные языки: 100 ru, 89 kk, 11 en. Язык интерфейса не является оценкой способностей или вовлечённости.

## Правила прогресса

Базовые уровни в `employees.skills` относятся к `last_review_date`. README говорит, что позднейшие завершения ещё не учтены. По полю `date` найдены 318 завершений после оценки у 133 сотрудников.

Для соответствующего завершения и навыка безопасная формула:

```text
after = max(before, min(before + gain, max_level, 5))
```

Уровень не должен снижаться, если он уже выше потолка конкретного курса. Применять каждое завершение только один раз; не начислять его повторно при обновлении страницы или повторном нажатии. Учитывать завершения до среза, не переигрывать всю историю поверх уже оценённых навыков.

### Неоднозначность даты

В CSV нет `completed_at`. Для `self_paced` поле `date` означает дату зачисления, а не завершения. Среди завершений с `date` после оценки таких строк 139. По набору нельзя точно определить момент завершения самостоятельного курса, начатого до оценки.

Предлагаемое допущение MVP: использовать `date` как приближение для исторического начисления и явно описать ограничение. У представителя кейса стоит уточнить ожидаемую трактовку. Для новых действий приложения сохранять собственную дату завершения.

### Повторные обязательные обучения

Общее правило README о неповторении завершённых мероприятий не описывает все фактические данные. Найдены 458 пар сотрудник–мероприятие с повторными завершениями вне клуба `EV_036`; все относятся к обязательным `EV_001`, `EV_002`, `EV_003`. У них пустой `develops_skills`, поэтому они не увеличивают навыки.

Сохранять эти записи как историю, не считать их дубликатами записей и не предлагать обязательное обучение как добровольный следующий шаг. Повторных завершений остальных добровольных мероприятий, кроме разрешённого клуба, не найдено.

## Предлагаемый MVP

1. Профиль: текущие навыки с учётом истории, цель, требования и пробелы.
2. Подбор: проверка роли/грейда, prerequisites, дат, повторов и полезного прироста; затем AI выбирает 1–3 активности среди допустимых с учётом нескольких факторов. Ответ модели проверяется по исходным данным.
3. Объяснение: цель и грейд, критические пробелы, история участия, конкретный ожидаемый прирост. Не обещать автоматическое повышение.
4. Завершение: одно действие обновляет прогресс с ограничениями `gain` и `max_level` и сохраняется без двойного начисления.
5. HR: общие пробелы, участие и случаи без следующего шага; разграничение доступа к индивидуальным сведениям.
6. Импорт: дополнительные профили и история в схеме организаторов, валидация ссылок, предварительный просмотр ошибок и явная стратегия слияния данных.

Минимальные проверочные сценарии: сотрудник без цели; смена роли; Lead; не выполнены prerequisites; завершённый курс; повторяемый клуб; навык выше потолка курса; история после оценки; повторное завершение в интерфейсе; импорт неизвестного профиля; недоступность AI API.

Объём набора позволяет считать правила и статистику локально. GPU для предлагаемого MVP не требуется. Выбор модели, стека и реализация остаются отдельным этапом.
