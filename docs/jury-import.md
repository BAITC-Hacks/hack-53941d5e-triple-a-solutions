# Импорт профилей и истории жюри

Запустите `node scripts/serve.mjs` или `start-prototype.cmd`, откройте раздел **Данные жюри**.
Нужен Node-сервер: статический Python preview не обслуживает импорт и AI.

1. Выберите JSON с профилями и/или CSV/JSON с историей.
2. Нажмите **Проверить файлы**: увидите новые записи, замены, пропуски и ошибки.
3. Проверьте список, затем нажмите **Применить импорт**.
4. Откройте **Мой рост** и выберите нового сотрудника. Теперь он доступен и серверным AI-сценариям.

Для знакомства используйте вымышленные `data/examples/jury-employees.json` и
`data/examples/jury-history.csv` вместе. История без нового профиля будет отклонена.
Сам импорт не отправляет данные провайдеру AI.

## Форматы

Профили: массив, объект `{ "employees": [...] }` либо один профиль.
Обязательны `employee_id`, `role`, `grade`, `skills`, `last_review_date`.
`full_name` можно опустить — вместо него показывается ID.
`career_goal` — `null` либо `{ "target_role": "Backend Engineer", "target_grade": "Middle" }`.
Роль/грейд и цель должны присутствовать в текущих roleProfiles, навыки — в skills.
Уровни — целые 0–5, пропущенные навыки считаются нулевыми.
ID — латинские буквы, цифры, `_`, `-`, до 80 символов.

Уровни профиля должны соответствовать дате `last_review_date`. Приложение добавляет
прирост за завершения **после** неё, поэтому не загружайте одновременно уже обновлённые
уровни со старой датой оценки: это даст двойной учёт. Используйте реальную дату оценки
из синтетического набора. Даты оценки и истории — YYYY-MM-DD, не позже `asOf`
текущего каталога (в текущем снимке 2026-10-01).

CSV: UTF-8, запятая; BOM, CRLF, кавычки и переносы внутри полей поддерживаются.
Обязательные колонки: `record_id,employee_id,event_id,date,status`.
Необязательные: `due_date,completion_pct,score,feedback_rating,assigned_by`.
Статусы: `completed,in_progress,dropped,no_show,declined,overdue`.
Процент и оценка — 0–100, feedback_rating — 0–5. Историю можно передать и как JSON-массив
или объект `{ "history": [...] }` с теми же полями. `employee_id` должен ссылаться на
существующий/импортируемый профиль, `event_id` — на существующий каталог.
Неизвестные поля не используются. Каталоги активностей, навыков и должностей этим экраном не импортируются.

## Конфликты и хранение

Добавление — по ID, не по имени. Совпадающая запись пропускается. Разные записи с одним
ID отклоняются, пока явно не включена замена. Замена профиля сохраняет его историю;
история заменяется только по своему record_id. Повторяющиеся ID внутри входного файла
отклоняются. При любой ошибке не применяется весь пакет.

Лимит: 5 МБ файлов за импорт, до 1000 сотрудников и 20 000 записей истории в итоговом наборе.
Предпросмотр действителен 10 минут и только для проверенной версии данных.
Изменение файлов/режима замены требует нового предпросмотра. Устаревшие вкладки получают
сообщение обновить страницу, чтобы AI не считал по другому набору.

Исходный `src/prototype/data.json` не меняется. Локальный снимок и один предыдущий набор
сохраняются атомарно в **artifacts/imported-dataset.json**, исключённом из Git и статической
раздачи. **Отменить последний импорт** возвращает предыдущий набор, в том числе после
перезапуска. При обновлении исходного каталога сохранённый импорт нужно сначала вынести
в резервную копию, затем повторить на новом каталоге; сервер сообщает о несовпадении версий.

Локальные цели, демо-прогресс, планы и HR-черновики привязаны к набору данных. После его
замены старые сохранения не используются; отмена импорта не гарантирует возврат этих
браузерных черновиков, если они были перезаписаны после импорта. Между ноутбуками импорт
и localStorage не синхронизируются — каждый член команды загружает свои тестовые файлы.

Это локальный прототип без входа и разграничения ролей. Используйте синтетические данные.
Условия кейса ограничивают вынос данных за пределы хакатона; перед вызовами AI с данными
организаторов уточните разрешение на передачу выбранному провайдеру. Для проверки подключения
есть `node scripts/check-ai-workflows.mjs --live`: он использует только придуманные примеры.
